# 所持キャラ名鑑

HoYoLAB の「全キャラクター」画面からコピーした文字列を貼り付けて、**自分が所持しているキャラだけ**を棚に並べて眺めるための静的サイト。

「今日これをやれ」と指示する計画屋ではなく、問い合わせたときだけ答える辞書として作っている。育成進捗トラッキング・Todo・ダメージ計算・ビルド推奨・外部アカウント連携は意図的に入れていない。

## 動かす

完全な静的サイトで、サーバサイド処理はない。ペースト・解析・照合・描画のすべてがブラウザ内で完結し、実行時に外部へ通信しない。

```sh
npm run serve      # http://localhost:8000
```

ES モジュールを使っているため `file://` で直接開くと読み込めない。ローカル確認には上記のような HTTP サーバが要る（GitHub Pages 上では不要）。

## 公開する（GitHub Pages）

ビルド成果物はコミット済みなので、`main` を Pages に向けるだけでよい。

1. 実装を `main` にマージする（Pages はブランチの内容を配信するため、`main` に無いものは公開されない）
2. リポジトリの Settings → Pages
3. Source を **Deploy from a branch**、Branch を **`main`**、フォルダを **`/ (root)`** にして Save
4. 1 分ほどで `https://takoyakibot.github.io/gnsn/` で見られる

マージ前に確認したいときは、手順 3 の Branch に作業ブランチを指定すればそのまま配信される。

パスはすべて相対にしてあるので、`/gnsn/` のようなサブディレクトリ配信でもそのまま動く。`.nojekyll` を置いて Jekyll のビルドを経由させていない（素の静的ファイルなので通す意味がなく、ビルド失敗という失敗要因を持ち込まないため）。

以降は `main` へのマージのたびに自動で再デプロイされる。属性データ更新の PR をマージすれば、それも自動で反映される。

## 構成

```
index.html            画面とスタイル
app.js                描画・絞り込み・編成メモ・素材ダイアログ（DOM 操作のみ）
parse.js              HoYoLAB のコピー文字列のパーサ
roster.js             パース結果と属性データの突き合わせ・共鳴判定
materials.js          突破素材・天賦素材の並べ替えと秘境の曜日判定
names.js              名前の正規化と照合キー
data/characters.json  キャラ属性データ（生成物・コミット対象）
data/materials.json   突破素材・天賦素材とモラ早見表（生成物・コミット対象）
tools/build.mjs       genshin-db から上記 JSON を生成
tools/aliases.json    HoYoLAB 表記 → genshin-db 表記の別名テーブル
test/                 node --test で走る検証
manifest.webmanifest  ホーム画面から起動するための PWA manifest
icons/                アイコン（icon.svg が元データ・PNG は書き出し）
.github/workflows/    属性データの定期再生成
```

`npm` が必要なのは属性データを作り直すときだけで、サイトを表示するのにも直すのにも要らない。バンドラもフレームワークもテストランナーも入れていない。

## 属性データの更新

パースで得られるのは名前・レベル・凸数だけなので、元素・武器種・レアリティは名前をキーに [genshin-db](https://www.npmjs.com/package/genshin-db) と照合している。実行時には叩かず、ビルド時に静的 JSON へ焼き込む。

```sh
npm ci
npm run build:data
npm test
```

ビルドは以下のいずれかで**非ゼロ終了して JSON を書かない**。黙って古いデータのまま成功させないための作りなので、失敗したらメッセージに出た名前を調べること。

- genshin-db から属性を取得できないキャラがいる
- `tools/aliases.json` の参照先が genshin-db に存在しない
- 照合キーが 2 キャラで衝突する

### 定期再生成（GitHub Actions）

`.github/workflows/update-characters-data.yml` が毎週月曜に再生成を試み、**差分があれば PR を作る**（`workflow_dispatch` で手動実行もできる）。差分がなければ何もせず終わる。

main へ直接コミットはしない。ビルドは上記の 3 つでは失敗するが、「新キャラが 2 人増えただけ」は正常に成功する。つまり見慣れない名前が黙って main に入りうるので、PR の差分を見てからマージする形にしている。PR 本文には追加・変更・削除されたキャラと確認事項が入る。

ゲーム内で新キャラが実装されても genshin-db 側のデータが更新されるまでは空振りになるため、実装直後を狙って回しても意味がない。上流の公開タイミングは制御できないので、狙わずに短い間隔で拾いに行く方針にしている。この待ち時間のあいだ、該当キャラは `?` として表示される（後述）。

#### cron の自動停止について

パブリックリポジトリの scheduled workflow は、**60 日間リポジトリ活動がないと GitHub 側で自動的に無効化される**。活動として数えられるのは実質コミットだけで、タグやリリースの作成では防げない。

このリポジトリで活動の実体になるのは「このワークフローが出した PR のマージ」なので、上流の genshin-db が静かな期間はマージする対象そのものが存在せず、活動が途切れて cron が止まる。そして止まったあとは genshin-db が更新されても回らない。**cron を生かしている活動が cron 自身の産物**という循環になっている。

新キャラが 3〜6 週間おきに増えて 1 週間以内にマージする運用なら計算上は 60 日に収まるが、復刻だけのパッチが挟まると余裕がなくなる。そのため最後のステップで毎回 enable API を叩き、先回りで無効化を防いでいる（`actions: write` が必要）。データ更新の成否とは無関係なので、このステップが失敗してもジョブは落とさない。

それでも止まってしまった場合は、Actions 画面か `gh workflow enable` で再有効化し、`workflow_dispatch` で手動実行すればよい。

なお cron が止まっても**データが静かに古くなるだけで、間違った属性が表示されることはない**。未収録のキャラは `?` として出るので、止まっていることは画面から気づける。

### 名前の揺れをどう吸収しているか

HoYoLAB の表記と genshin-db の表記は 2 通りの理由でずれる。扱いを分けている。

**機械的な揺れ**は `names.js` の `matchKey()` が吸収する。NFKC 正規化・空白除去・括弧の統一・異体字の畳み込みで照合キーを作るので、`ドール（女）` と `ドール(女)`、`兹白` と `茲白`、`雲菫` と `雲堇` はすべて同じキーになる。名前を列挙する必要はない。全キャラでキーが衝突しないことをビルドとテストの両方で検査している。

**意味的に違う名前**だけを `tools/aliases.json` に書く。現時点では 1 件だけで、HoYoLAB が「旅人」と表示するキャラを genshin-db は「空」「蛍」で持っている。

元素可変キャラ（旅人・ドール（男）・ドール（女））は genshin-db 上で元素が `無` になっている。該当は 4 件のみで他に `無` はいないため、これを機械的に `可変` へ置き換えている。単一元素として扱うと元素共鳴を誤判定するため、共鳴の数え上げからは除外する。

### 照合できなかった名前について

genshin-db の日本語表記が HoYoLAB の表記と一致することは実データの 51 件で確認しているが、全 120 キャラ分を突き合わせる手段はない。加えて、新キャラ実装から属性データ再生成までのあいだは必ず未収録の名前が出る。

そのため、**推測で埋めずに `?` として表示し、照合できなかった名前を画面上に一覧で出す**方針を取っている。取りこぼしが見つかったら `tools/aliases.json` に 1 行足すか、データを作り直せばよい。

`localStorage` に保存するのはパース結果（名前・レベル・凸数）だけで、属性を結合したあとの状態は保存しない。そのため属性データを更新すると、それまで `?` だったキャラが貼り直しなしで解決する。

## テスト

```sh
npm test
```

依存パッケージなしで走る（`node --test` のみ）。仕様書の受け入れ基準に対応した検証が入っている。

- PC 版・スマホ版のどちらの入力からも同一の 51 件が得られる
- 全角括弧と半角括弧、異体字が同一キャラとして照合される
- 入力の途中に不正な文字列を挿入しても前後のキャラが取得できる
- 解析できない行（PC 版末尾の `11` を含む）がキャラとして数えられない
- 属性データに無い名前が推測値で埋められない
- 元素可変キャラを含む編成で元素共鳴が誤判定されない
- 素材が数量やレアリティ段階を持たず、1 つに畳まれている
- 突破のボス素材と天賦の週ボス素材が混ざらない（`typeText` が同じため出現箇所で分けている）
- 素材データが無いキャラで捏造が起きない
- モラ早見表の段階ラベルと累計が正しい
- 秘境の曜日が 04:00 切り替わりで判定される
- レベル帯が Lv.1〜90 を隙間も重なりもなく覆い、境界が正しい

`test/fixtures/roster-pc.txt` は実際のコピー結果。`test/fixtures/roster-sp.txt` はスマホ版の抜粋と形式定義から同一ロスターを再構成したもので、生キャプチャではない（制御文字・私用領域の文字も混ぜてある）。

## パーサについて

入力形式は PC 版とスマホ版で異なる。PC 版は `Lv.XX` → 凸数（独立行・凸0なら行ごと無い）→ 名前。スマホ版は `Lv.XX` → `名前 凸数` の同一行で、括弧が半角、エントリ間に空行が入り、画像も一緒にコピーされるため制御文字や私用領域の文字が混入する。

パターンに一致した行だけを拾い、それ以外は破棄して次へ進むホワイトリスト方式にしている。異物は末尾に来るとは限らず、途中で混ざったときに解析を打ち切ると以降のデータが全損するため。

破棄した行は `parse()` の戻り値に含まれるが、**画面には出さない**。`11` のような意味のない残骸を並べても読む側の役に立たないため。画面に出す警告は「属性データと照合できなかったキャラ名」だけに絞っている。

前処理では**行分割を制御文字の除去より先に行う**こと。順序を逆にすると改行自体が制御文字として除去され、入力全体が 1 行に潰れて何も取得できなくなる。

PC 版のコピー結果の最終行には必ず `11` が付く。所持数・満凸数・★5数のいずれとも一致せず凸の上限も超えるため、意味のある値ではないと判断して破棄している。

## 取り込み

入力元は HoYoLAB の戦績（Battle Chronicle）の「全キャラクター」画面のテキストコピー。取得手順は画面の「どこからコピーするの？」に出しているので、初めて開いた人が迷わないようにしてある。

1. HoYoLAB にログインして原神の戦績を開く（ゲームアカウントの連携と戦績の有効化が必要）
2. 「キャラクター」の欄から全キャラクターの一覧を開く
3. 画面のテキストを全選択してコピー（PC は Ctrl+A → Ctrl+C、スマホは長押しして「すべて選択」）
4. 貼り付けて「解析する」

**画面に置くリンクには個人パラメータを含めない。** 戦績の URL には `user_id` と `role_id`（ゲーム内 UID）が入るため、そのまま埋め込むと公開リポジトリで特定個人の識別子を晒すことになる。ログイン済みなら自分の戦績に解決される汎用の入り口だけを置いている。

ログインや cookie の連携は要求しない。貼り付けたテキストはブラウザ内だけで処理し、外部へは送信しない。

## 絞り込み

元素と武器種は**選ぶと絞る**（複数選択）。レベル帯は逆に**押すと隠す**除外方式で、育て終わったキャラや放置しているキャラを視界から外すのに使う。向きが逆なので、隠した帯は取り消し線と薄い表示で区別している。

所持キャラに 1 人もいない値はチップ自体を出さない（元素不明が 0 人なら `?` も出ない）。判定は絞り込み前の全件に対して行うので、絞るほどチップが消えて戻せなくなることはない。

## 突破素材・天賦素材

**編成メモ / 育成予定の枠に入れたキャラ**に「素材」ボタンが出る。棚のカードはクリックで枠に出し入れするだけに使う。`data/materials.json` は棚の描画には要らないので、素材を初めて開いたときにだけ読み込む。

**数量とレアリティ段階は持たない。** 出すのは「何を集めるのか」だけで、必要個数・所持数・進捗は扱わない。そのためビルド時に段階を畳んでいる。

| 種別 | 表示 | 畳み方 |
|---|---|---|
| 宝石 | `炎願のアゲート` | `·砕屑` `·欠片` `·塊` を落として 1 つに |
| ボス素材 | `常燃の火種 ← 爆炎樹` | 入手元を添える |
| 特産品 | `絶雲の唐辛子` | そのまま |
| 天賦本 | `「勤労」` | `の教え` `の導き` `の哲学` を落として 1 つに |
| 週ボス素材 | `東風の爪 ← 風魔龍` | 入手元を添える |
| 冠 | `知恵の冠` | そのまま |
| ドロップ元 | `スライム` | 3 段階をドロップ元の敵名へ寄せて 1 つに |

共通素材（雑魚ドロップ）は段階ごとに語幹が違うため接尾辞では畳めない（`破損した仮面` / `汚れた仮面` / `不吉な仮面`）。代わりに genshin-db の `sources` からドロップ元の敵名を取っている。突破と天賦でドロップ元が一致する場合は「共通」として一度だけ出す。

`sources` の書式（`スライムがドロップ` / `風魔龍（Lv.70以上）挑戦報酬` / `Lv.30以上の守護者・堕天がドロップ`）に当てはまらないものが出たらビルドを失敗させる。変な文字列がそのまま画面に出るのを防ぐため。宝石・天賦本・共通素材が 1 つに畳めない場合も同じく失敗する。

天賦本には秘境名と入手曜日が付く。今日入手できる場合は小さなバッジを出すが、それ以上は踏み込まない（「今日これをやれ」と指示する道具にはしない方針のため）。曜日は端末の日付を基準に 04:00 切り替わりで判定しており、サーバ選択までは見ていないので実際のリセット時刻とは最大 1 時間ずれうる。

モラの必要額は**全キャラ共通**だったので、キャラごとには持たせず「モラ早見表」として段階別・累計の一覧にしている。共通でないキャラが現れたらビルドが失敗する。

genshin-db 側にデータが無い節は `?` と同じ扱いで「データがありません」と出し、推測で埋めない。現時点では旅人（元素可変のため天賦データなし）とドール（男/女）（突破コストがモラ 0 のみ）が該当する。

## 編成メモ / 育成予定

4 枠にカードを出し入れして元素共鳴を確認するための軽いメモ。育成予定のキャラを置いておく用途と兼用で、選択は `localStorage` に保存されるので次に開いたときもそのまま残る。所持キャラから消えたキャラは自動的に枠から外れる。

枠に入れたキャラには「素材」ボタンが付く。突破素材・天賦素材を見るのはここから。

「枠を空にする」は確認を挟む（保存された選択を消す操作なので）。枠が空のときは何も起きない。

進捗の記録・チェックリスト・通知は持たない。

## PWA について

`manifest.webmanifest` を入れてあるので、スマホのホーム画面に追加すると単体アプリのように起動する。パスはすべて相対にしてあり、GitHub Pages のサブディレクトリ公開でもそのまま動く。

**Service Worker は意図的に入れていない。** キャッシュが `data/characters.json` の更新を妨げ、`?` のままのキャラが直らなくなるため。上の「照合できなかった名前について」で書いた「データを更新すれば貼り直しなしで解決する」という性質と正面から衝突する。オフライン起動が必要になったら、データだけ network-first にするなど、鮮度を壊さない形で別途足すこと。

アイコンは `icons/icon.svg` が元データで、PNG はそこからの書き出し。公式のイラスト・ロゴ・マーク等は使っていない（棚に並ぶ背表紙を元素の色で表した自作の図案）。

## 素材について

キャラクターアイコン等の公式画像は使用していない。二次創作ガイドラインで公式作品の直接二次利用が禁止されているため、テキストと自作の色分けで表現している。
